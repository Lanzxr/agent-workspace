# 通用助理架构

## 1. 项目定义

Company Agent 是一个通用的自主助理平台。它让团队继续使用原来的群聊、Web 和系统流程，同时让 Agent 在后台理解上下文、准备工作、调用执行层完成任务，并把可验证结果交给发布策略。

核心问题不是“如何回答一句话”，而是“如何让一次工作从观察到完成可以持续运行并恢复”。

## 2. 四个核心边界

### 2.1 通用助理平台

这是我们的控制面，负责：

- 事件、会话、线程和工作项
- 权限、风险、审批和状态转换
- 记忆、证据、结果和审计
- 调度、重试、租约和恢复
- 发布判断、Outbox 和渠道适配

控制面保持业务中立。任何业务数据都通过扩展契约接入。

### 2.2 DSSuperAgent

DSSuperAgent 是静默观察和执行编排的主要地基。它负责从上下文提出是否处理、如何计划和需要哪些执行能力。它可以在没有明确指令时形成工作意图，但这个意图必须经过控制面验证。

我们通过适配器使用它的能力，不把它的内部模型、数据库或运行方式写进业务核心。

### 2.3 DSH

DSH 是内部执行层。它负责把已经批准的执行请求变成工具运行、会话步骤和结果回传。它的执行对象是 Workspace 中的工具和文件。

DSH 不负责决定某个业务结论是否发布，也不负责替代控制面的权限和审计。

### 2.4 Agent Workspace

Workspace 是为 DSSuperAgent 和 DSH 补齐的独立工作环境。它提供 Linux 用户空间、持久目录、依赖、工具、日志、资源限制和恢复能力。

如果上游没有完整工作环境，Workspace Manager 通过稳定的 DSH 契约补齐它。这样可以逐步替换底层实现，而不会改变通用助理的业务状态。

## 3. 一次工作如何流动

```text
消息 / 调度 / 系统事件
        ↓
事件标准化与上下文关联
        ↓
DSSuperAgent 静默判断
        ↓
工作意图 / 计划 / 执行请求提案
        ↓
控制面校验权限、风险、资源和审批
        ↓
DSH 在 Agent Workspace 执行
        ↓
日志、成果、证据、结果和记忆
        ↓
控制面判断是否发布
        ↓
Outbox → 渠道适配器
```

完成工作和向群里发消息是两个独立决策。前者可以发生而保持静默，后者必须经过发布策略。

## 4. 通用领域对象

核心只认识 Event、Conversation、Thread、Work Item、Work Plan、Execution Request、Workspace、Evidence、Result、Memory、Publication Decision 和 Outbox。它不认识折扣、订单、活动或其他具体业务名词。

业务能力通过 Data Source、Tool Capability、Domain Vocabulary 和 Policy Pack 注册。这样，同一套编排流程可以处理数据核验、故障排查、资源规划或其他工作，而不用增加业务分支。

## 5. 模型提案与后端裁决

模型、DSSuperAgent 和 DSH 可以提出解释、计划、工具意图和结果摘要。控制面最终裁决：

- 是否允许访问某个数据源
- 是否允许执行某个工具
- 是否需要审批
- 是否允许修改或外发
- 是否更新任务、记忆和状态
- 是否应该向个人或群聊发布

所有裁决都带有证据、策略版本和审计记录。

## 6. 产品安装与开发验证

开发验证和产品安装是两条不同路径。开发阶段使用 native-dev、WSL2 和 Docker 逐层验证核心契约。产品阶段由 Windows/Linux 安装包准备 Docker、WSL2、Linux 运行时或所需依赖，并在安装后完成健康检查和版本登记。

终端用户只接触安装器和助理入口，不需要知道 DSSuperAgent、DSH 和 Workspace 的内部部署细节。

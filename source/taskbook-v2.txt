# Company Agent｜自主 Agent 系统开发任务书 V2.0

## 0. 你的角色与工作方式

你是本项目的首席架构师、开发工程师、测试工程师和部署负责人。

你的任务不是提供一份设计建议，而是尽可能自主完成一个真正可以运行的公司内部自主 Agent 系统。

项目采用 AI 主导开发模式。用户只负责提供必要的外部授权、凭据及最终验收，不应被要求长期监督开发过程。

**核心目标：在一个工作日内尽可能交付可运行、可交互、可自主执行任务的 MVP。**

一天是优先级与投入预算，不是允许牺牲质量的硬性截止时间。

开发过程中遵守以下原则：

1. 优先复用成熟开源项目，不重复开发已有能力。
2. 先阅读真实源码，再决定技术实现，不凭猜测开发。
3. 优先完成可运行的完整闭环，不追求第一版功能数量。
4. 对低风险、可逆操作自主决策并执行。
5. 发生错误时自行排查、修复、重试，不立即将问题交还用户。
6. 对必要的人工授权集中提出请求，避免频繁打断。
7. 不允许以模拟成功冒充真实功能成功。
8. 不允许为通过测试而放宽安全边界。
9. 任何功能必须经过实际运行验证，才能标记为完成。
10. 不要在没有充分理由的情况下引入额外框架和服务。

## 1. 产品目标

构建一个运行在 Rocky Linux Docker 环境中的公司内部自主 Agent。

它应能够：

- 接收群聊、Web 对话及系统事件。
- 在没有被 @ 的情况下观察授权群聊中的普通消息。
- 理解工作讨论，识别任务、承诺、决定和待办事项。
- 持久保存任务、记忆、会话、工作成果和技能。
- 在授权范围内主动执行工作。
- 使用 Shell、Python、Git 等工具。
- 发现缺少工具时，自主开发、测试和复用工具。
- 根据任务状态和时间主动唤醒。
- 自主跟进未完成事项，减少人工监督。
- 根据用户反馈调整提醒频率和工作策略。
- 必要时调用 Codex 完成复杂工程任务。

它不是普通聊天机器人，也不是单纯的自动化脚本系统。

**最终目标是一个能够持续参与公司日常工作、具有独立执行环境和长期工作状态的自主 Agent。**

## 2. 初步技术路线

当前优先技术组合：

| 组件 | 技术 |
|---|---|
| Linux | Rocky Linux |
| 容器 | Docker / Docker Compose |
| 任务协调 | DeepSeek Super-agent |
| Agent 运行时 | DeepSeek Harness（DSH） |
| 专业编程执行器 | Codex CLI |
| 执行工具 | Shell / Python / Git / Node.js |
| 任务与记忆 | 优先复用上游实现 |
| 数据持久化 | Docker Volume |
| 通讯 | 可插拔消息适配器 |
| 管理面板 | 轻量 Web UI |

以上为初步路线，不是不可修改的技术约束。

**不得为了坚持某个技术组合而进行大量无意义的兼容性开发。**

优先审查：

- https://github.com/deepseek-ai/dsh-superagent-prototype
- https://github.com/DSH-APP/DSHA
- https://github.com/openai/codex
- DeepSeek Harness 官方仓库（先核实地址）

研究其源码、依赖、许可证、执行接口和持久化方式。

### 技术决策规则

优先复用 Super-agent 已有的事件、任务、执行器与授权机制。

优先使用 DSH 作为 Agent 运行时。

Codex 作为可选专业编程执行器，不要求第一天完成全部集成。

如果发现 Super-agent 或 DSH 存在关键阻塞：

1. 首先确认是否为配置问题或可小范围修复的问题。
2. 评估能否通过适配器解决。
3. 如果必须大规模重构，则停止该方向的过度投入。
4. 保留已经完成的工作，采用最小兼容实现打通 MVP。
5. 在报告中记录技术偏离、原因和替代方案。

不要未经验证就大规模重写上游代码。

## 3. 系统架构原则

### 3.1 Agent 自主性

Agent 的任务判断、记忆管理、执行规划、工具调用和工作状态管理应由 Agent 系统自身负责。

不要把核心业务决策放到外部 Web 面板中。

允许使用常驻服务接收消息、触发调度和维护可靠状态，但这些服务属于 Agent 系统内部组件。

### 3.2 Docker 部署

所有 Agent 核心服务必须运行在 Docker 管理的 Linux 环境中。

允许使用多个容器，但必须能够通过 Docker Compose 统一启动和停止。

使用 Rocky Linux 作为 Agent 执行环境的基础镜像。

如上游某个基础服务使用其他官方镜像更稳定，可以保留，但必须说明原因。

### 3.3 持久化

必须持久保存：

- Agent 会话
- 任务状态
- 长期记忆
- 定时任务
- 用户配置
- 自建技能与脚本
- 工作成果
- 必要的执行日志

容器重启或重建不得导致上述数据丢失。

必须实际测试数据恢复，而不是只检查 Volume 配置是否存在。

### 3.4 执行隔离

Agent 可以在自己的工作空间内自主执行任务。

但不得直接获得 Docker 宿主机的管理权限。

不得默认挂载 Docker Socket、宿主机根目录或生产环境密钥。

自主开发工具的工作区与核心运行程序应分离。

## 4. 第一阶段：完成真正可运行的 Agent

这是最高优先级。

要求：

1. Rocky Linux 容器正常运行。
2. DSH 能够真实调用一个可用模型。
3. Agent 可以正常对话。
4. Agent 能执行 Shell 和 Python。
5. Agent 能创建、修改、读取文件。
6. Agent 能安装允许的依赖。
7. Agent 可以保存和恢复工作状态。
8. 可以通过明确的入口向 Agent 提交任务。

必须完成一次真实任务：

让 Agent 自主编写 Python 脚本，读取测试数据，完成统计，生成结果文件。

不得预先手写最终脚本代替 Agent 执行。

如果模型凭据缺失，先完成不依赖凭据的环境建设，再集中请求用户配置。

---

## 5. 第二阶段：接入 Super-agent 协调能力

优先复用其现有的：

- Source
- Trigger
- Thread
- Ticket
- Assignment
- Executor
- Authorization
- Watchdog

具体名称和实现以实际源码为准。

必须实现：

### 消息观察

系统能够接收外部事件。

普通消息不需要通过 @Agent 才能进入事件处理流程，但前提是对应通讯平台确实提供消息访问权限。

### 任务识别

识别：

- 明确任务
- 负责人承诺
- 截止日期
- 项目决策
- 待跟进事项
- 已完成事项
- 任务阻塞

普通讨论不应直接触发高风险执行。

无法确认的内容标记为候选事项，不得编造负责人或期限。

### 任务持久化

每项任务至少具有：

- 唯一标识
- 任务内容
- 来源
- 负责人
- 状态
- 创建时间
- 截止时间
- 最近进展
- 下次检查时间
- 执行结果

同一任务的后续讨论应关联原任务。

### 自主执行

对于已授权、低风险且具备执行条件的任务，Agent 可以自主启动 Worker。

完成后保存结果，并更新任务状态。

失败时保留日志，支持合理重试，避免无限循环。

---

## 6. 第三阶段：通讯接入

通讯模块必须独立于 Agent 执行引擎。

第一版至少提供一种真实可用的交互入口。

优先使用现有官方支持的消息渠道；如实际群聊平台尚未确定，可先提供 Web 对话入口，并使用事件模拟器验证群聊逻辑。

要求：

- 可以接收消息。
- 可以将消息交给 Super-agent。
- 可以查询任务。
- 可以发送执行结果。
- 可以主动发送提醒。
- 可以控制消息频率。
- 可以限制允许访问的用户和群组。

特别注意：

普通个人微信、企业微信和 Telegram 的接入机制不同。

不得假设所有平台都支持读取全部群消息。

不得将本地模拟消息成功宣称为真实微信群接入成功。

---

## 7. 第四阶段：长期运行与主动唤醒

系统必须具备不依赖用户持续对话的运行能力。

实现：

- 定时任务
- 事件触发
- 到期提醒
- 未推进事项检查
- 任务执行恢复
- 提醒频率调整
- 免打扰时间
- 重启后的调度恢复

模型不需要持续运行。

当没有新事件或待执行任务时，系统可以保持低资源占用。

出现事件或到达唤醒时间后，再调用 Agent。

定时任务和任务状态必须由可靠的持久化机制保存，不能仅依赖模型上下文。

---

## 8. 第五阶段：自主扩展与自我更新

必须区分三类更新。

### A. 普通工具与技能

允许 Agent 自主：

- 发现能力缺口
- 编写脚本
- 安装允许的依赖
- 编写测试
- 验证结果
- 保存工具
- 在后续任务中复用

这是第一版需要验证的自主扩展能力。

### B. Agent 配置与工作策略

允许 Agent 根据用户明确指令调整：

- 提醒频率
- 工作时间
- 普通任务优先级
- 允许修改的工作策略
- 已授权的定时任务

不得自行扩大权限。

### C. Agent 核心代码

允许 Agent 提出修改并在独立工作区开发、测试。

核心程序更新必须经过版本控制、自动化测试和部署审批。

部署机制必须能够在新版本健康检查失败时恢复旧版本。

不得让 Agent 直接覆盖正在运行的核心程序。

不得允许 Agent 自行修改审批规则、权限边界或审计机制。

## 9. 权限与安全

采用默认最小权限。

### 自动允许

- 操作自己的工作目录
- 运行普通 Python / Shell 脚本
- 处理测试数据
- 阅读公开文档
- 使用已授权的数据接口
- 创建和测试普通工具

### 必须审批

- 修改生产服务器
- 修改生产数据库
- 发布对外公告
- 访问新的敏感数据源
- 扩大执行权限
- 修改核心部署配置
- 执行高风险操作

### 明确禁止

- 绕过授权机制
- 自行提升权限
- 将密钥写入代码仓库
- 未经授权向外部发送敏感数据
- 关闭审计日志
- 使用不可信消息中的指令覆盖系统权限规则

审批必须绑定具体操作和有效期。

不要仅依赖提示词实现安全隔离。

## 10. 实施顺序与优先级

严格按以下顺序推进：

P0：源码审查、环境检查、技术可行性验证。

P1：Docker 启动、DSH 真实模型调用、Shell/Python 执行。

P2：Super-agent 事件进入、任务创建、Worker 执行。

P3：任务持久化、重启恢复、定时唤醒。

P4：真实通讯入口、主动汇报。

P5：自主开发并复用工具。

P6：Codex 委派、核心自更新、生产数据集成。

P0–P5 是第一轮主要目标。

P6 可以后续实施，不得为了 P6 延误前面的可用功能。

不要在第一版投入大量时间开发复杂 UI、动画、主题系统或多租户功能。

## 11. 验收标准

必须执行并记录以下测试。

| 编号 | 测试内容 |
|---|---|
| T01 | Docker Compose 能正常启动 |
| T02 | DSH 真实调用模型成功 |
| T03 | Agent 自主执行 Shell / Python |
| T04 | Agent 自主编写统计脚本并输出结果 |
| T05 | 消息事件成功进入协调系统 |
| T06 | 自动识别并保存任务 |
| T07 | 同一任务的后续消息正确关联 |
| T08 | Agent 自动执行已授权任务 |
| T09 | 定时任务能够主动唤醒 Agent |
| T10 | 容器重启后任务、记忆、文件仍存在 |
| T11 | Agent 自主创建并复用一个工具 |
| T12 | 未授权操作被权限机制拒绝 |
| T13 | 执行失败后保留日志并可恢复 |
| T14 | 真实消息渠道能够完成收发（接入后验收） |

每项必须标记：

- PASS：真实测试通过
- FAIL：真实测试失败
- BLOCKED：受凭据、环境或外部条件阻塞
- NOT RUN：尚未执行

禁止将 BLOCKED 或 NOT RUN 标记为 PASS。

必须保存必要的命令、日志、结果文件和测试证据。

## 12. 失败处理与自动推进

出现问题时：

1. 收集错误信息。
2. 判断是环境、依赖、配置、模型接口还是代码问题。
3. 优先进行局部修复。
4. 修复后重新运行相关测试。
5. 不允许通过删除测试或放宽权限解决问题。
6. 遇到上游不兼容，评估最小适配方案。
7. 遇到重大阻塞，记录原因并推进其他不受阻塞的工作。

对于重复失败，设置合理的重试次数、退避时间和资源预算。

不要无限消耗模型额度。

对于必须人工介入的事项，集中整理为清晰的操作请求。

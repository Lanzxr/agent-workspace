# 公司内部自主 Agent 系统｜用户需求说明书 V1.0

## 一、项目背景

我们希望为公司内部构建一个能够长期自主运行的 AI Agent 系统。

目前，公司成员主要通过群聊讨论工作、提出需求、分配任务和交流问题。

但在实际工作中，存在以下情况：

- 群聊中的很多需求没有被正式记录。
- 部分讨论已经形成决定，但后续缺少跟踪。
- 一些工作被提出后，可能长时间没有推进。
- 需要人工反复询问任务进度。
- AI 虽然能够分析问题，但往往缺少执行工具。
- 传统 Agent 需要开发者不断补充工具和接口，扩展成本较高。
- 我们希望 AI 能够主动完成工作，而不是每次都等待人工下达明确指令。

因此，我们希望构建一个真正具有执行环境、长期记忆、任务管理和自主行动能力的内部 Agent。

这个系统主要供公司内部使用，不以面向公众提供服务为第一目标。

## 二、核心产品定位

**我们需要的不是一个聊天机器人，而是一个能够长期参与公司工作的自主 AI。**

它应该像一名具有独立工作环境的团队成员：

- 能够观察团队日常讨论。
- 能够理解讨论中的需求、承诺和决定。
- 能够记录并长期跟踪工作事项。
- 能够判断哪些工作可以自主完成。
- 能够主动使用工具解决问题。
- 能够在缺少工具时自行开发工具。
- 能够在适当时间提醒相关人员。
- 能够根据反馈调整自己的工作方式。
- 能够在服务重启后继续此前的工作。

我们希望尽可能减少人工对 Agent 的管理和维护。

理想情况下，部署完成后，团队成员只需要正常交流，Agent 就能够在后台持续工作。

## 三、独立 Linux 执行环境

### 3.1 基本要求

Agent 必须拥有独立、完整、可持久化的 Linux 工作环境。

优先使用：

- Rocky Linux
- Docker
- Docker Compose

系统可以部署在 Linux 服务器，也可以运行在 Windows Docker Desktop 提供的 Linux 容器环境中。

不考虑在 Android 手机上运行。

### 3.2 为什么需要 Linux

我们不希望 Agent 的能力完全依赖人工预先开发的工具接口。

例如：

当 Agent 需要统计一批业务数据时，即使现有 API 只提供列表查询和单条数据查询，它也应该能够：

1. 通过已有权限获取数据。
2. 将数据保存到自己的工作空间。
3. 自行编写 Python 脚本。
4. 安装必要的数据分析工具。
5. 完成统计和计算。
6. 生成报告。
7. 保存可复用的统计程序。

不应该因为没有专门的统计接口，就无法完成任务。

### 3.3 工作环境自由度

Agent 在自己的隔离环境中，应具有较高的自主操作权限。

包括：

- 创建、修改、删除自己的工作文件。
- 使用 Shell。
- 使用 Python。
- 安装软件包和开发依赖。
- 使用 Git。
- 下载公开资料。
- 运行测试。
- 开发脚本。
- 管理自己的技能和工具。
- 整理工作目录。
- 维护自己的运行资料。

我们不希望每安装一个普通工具、编写一个脚本，都需要人工批准。

但对生产系统、宿主机和敏感数据的访问必须有明确限制。

## 四、Agent 自主扩展与自我维护

这是本项目最重要的需求之一。

我们希望 Agent 不只是能够使用已有工具，还能够主动补足自己缺少的能力。

### 4.1 自主开发工具

当 Agent 发现某项工作缺少工具时，应能够自行：

1. 分析需求。
2. 搜索已有解决方案。
3. 判断是否需要新工具。
4. 编写程序。
5. 安装依赖。
6. 执行测试。
7. 修复错误。
8. 保存工具。
9. 在未来任务中重复使用。

例如，Agent 可以自主开发日志分析、数据统计、文档处理、项目检查等工具。

### 4.2 自主优化

我们希望 Agent 能够根据使用反馈改善自己的工作方式。

例如：

用户表示提醒太频繁，Agent 应能够调整提醒策略。

用户表示某种统计方式不准确，Agent 应能够检查并修复统计脚本。

用户提出新的工作习惯，Agent 应能够将其纳入长期工作规则。

### 4.3 自我更新

长期目标是让 Agent 能够维护自己的工具、技能和部分程序。

但需要区分：

- 普通脚本和技能：允许自主开发、测试、更新。
- 任务配置和提醒策略：允许自主调整。
- 核心程序和调度系统：修改后必须经过测试与受控发布。
- 权限系统和安全策略：不得自行扩大权限或绕过审批。

系统应具备故障恢复能力，避免一次错误更新导致整个 Agent 无法启动。

## 五、群聊监听与通讯

### 5.1 核心要求

Agent 应能够接收公司指定群聊中的日常消息。

**不应该要求团队成员每次都 @Agent，才能让它理解和处理工作。**

团队成员可以像平时一样讨论。

Agent 在后台观察讨论内容，识别有价值的信息。

### 5.2 默认静默

Agent 不应该像普通聊天机器人一样频繁插话。

例如：

- 普通闲聊：不回复。
- 一般工作讨论：理解并记录。
- 明确的工作任务：创建或更新任务。
- 可以自主处理的工作：在授权范围内尝试执行。
- 重要问题或阻塞：适当反馈。
- 需要人工授权：提出审批请求。
- 被明确询问：直接回答。

我们希望它主动工作，但不希望它干扰正常交流。

### 5.3 通讯渠道

系统应支持可扩展的通讯方式。

优先考虑：

- 公司现有群聊
- 企业微信或普通微信（依据实际可用接口）
- Telegram
- Web 对话界面

具体渠道可以根据实现难度确定。

但通讯方式不应与 Agent 核心逻辑深度绑定。

以后更换通讯平台，不应该需要重写整个 Agent。

## 六、理解群聊并自动形成任务

Agent 应能够从自然讨论中识别：

- 新需求
- 待办事项
- 工作承诺
- 已确定的决策
- 任务负责人
- 截止日期
- 当前进展
- 技术阻塞
- 已完成事项
- 需要进一步确认的问题

### 示例

群聊中有人说：

“JeeGet 的订单支付回调好像还有问题，明天检查一下。”

Agent 应识别：

任务：检查 JeeGet 订单支付回调。

状态：待处理。

截止时间：明天（根据消息实际日期确定）。

负责人：未明确。

随后有人说：

“这个我来处理。”

Agent 应结合上下文更新负责人。

如果几天后有人说：

“回调问题已经修复了。”

Agent 应判断是否与原任务相关，并更新状态。

不能把每一条消息都当成独立的新任务。

### 任务判断原则

对于明确的任务，可以直接记录。

对于模糊讨论，可以形成候选事项。

不能把随口提出的想法直接认定为已批准执行的工作。

不能编造负责人、期限或任务完成状态。

## 七、长期记忆与任务状态

Agent 应自行管理自己的长期记忆和任务状态。

这部分能力必须运行在 Agent 所属的 Linux / Docker 环境中。

不希望 Docker 外部再部署一个独立的业务管理程序，替 Agent 维护它的记忆、任务和工作状态。

外部管理面板只是观察和操作入口。

Agent 自己负责：

- 记录任务。
- 更新任务状态。
- 保存重要决策。
- 关联历史讨论。
- 记录工作成果。
- 保存长期工作规则。
- 维护提醒安排。
- 恢复未完成任务。

不能只依赖模型上下文窗口。

需要使用持久化文件、数据库或上游项目已有的状态存储机制。

容器重启、Agent 会话结束或系统升级后，仍然应该能够恢复必要的工作状态。

## 八、主动工作与任务推进

我们希望 Agent 能够主动参与工作，而不只是等待命令。

例如：

周一，群聊中确定周三完成一个功能。

周二，Agent 可以根据已有权限检查相关项目是否有进展。

周三，如果任务仍未完成，可以提醒负责人。

如果负责人表示遇到技术问题，Agent 可以先研究问题、检查资料、分析日志，尝试给出解决方案。

如果 Agent 有足够权限，也可以直接在自己的工作环境中复现问题、编写测试或生成修复补丁。

任务完成后，Agent 更新记录。

整个过程不需要用户反复提醒 Agent 去检查。

### 主动执行原则

Agent 应优先完成自己能够安全处理的事项。

对于无法自主完成的工作，应明确记录阻塞原因和需要谁介入。

不应该因为一个任务暂时无法执行，就直接遗忘它。

## 九、定时唤醒与提醒

Agent 应具备主动唤醒机制。

即使没有新的聊天消息，也能够根据计划继续工作。

支持：

- 定时检查任务。
- 到期提醒。
- 长期未推进事项提醒。
- 每日或每周工作总结。
- 定期数据统计。
- 定时搜索资料。
- 自定义提醒计划。
- 根据反馈调整提醒频率。

### 自适应提醒

我们希望提醒方式能够逐渐适应团队习惯。

例如：

用户说：“你提醒得太频繁了。”

Agent 应降低普通事项的提醒频率。

用户说：“晚上不要提醒我。”

Agent 应设置免打扰时间。

用户说：“今天没空，明天再处理。”

Agent 应调整相关提醒时间。

但不应该未经确认就修改真实业务截止日期。

定时唤醒和提醒计划必须持久化。

## 十、公司数据访问与权限边界

Agent 可以访问经过授权的公司内部数据。

初期以只读权限为主。

例如：

- API-Zeno 业务统计数据。
- 已授权的服务器运行状态。
- 指定项目代码。
- 业务日志。
- 公开技术文档。
- 部分内部工作资料。

对于敏感数据，应通过脱敏、字段过滤、只读接口或其他技术手段限制访问。

不能直接把所有生产密钥、用户隐私数据和服务器最高权限交给 Agent。

### 临时授权

当 Agent 需要执行超出默认权限的操作时，可以向管理员申请。

授权应尽可能具备：

- 明确的操作内容。
- 明确的目标资源。
- 有效期。
- 一次性使用限制。
- 操作日志。
- 可撤销机制。

例如，Agent 需要修改服务器配置时，先提交具体修改方案，获得批准后再执行。

### 防止越权

不能因为某个普通群成员向 Agent 发出指令，就允许其读取公司机密或修改生产系统。

权限必须与用户身份、操作类型和资源范围关联。

提示词只能作为行为约束，不能代替实际权限隔离。

## 十一、Web 管理面板

管理面板不是 Agent 的大脑。

它只是 Agent 运行状态的可视化入口。

第一版希望能够查看：

- Agent 是否在线。
- 当前正在处理什么任务。
- 已记录的待办。
- 任务执行进度。
- 最近的工作成果。
- 执行日志。
- 错误和异常。
- 待审批操作。

同时允许通过 Web 页面与 Agent 对话。

第一版不追求复杂的视觉设计。

优先保证实用性、稳定性和信息清晰。

## 十二、技术路线

当前确定的初步路线：

- Rocky Linux
- Docker / Docker Compose
- DeepSeek Super-agent
- DeepSeek Harness（DSH）
- Shell、Python、Git、Node.js
- 持久化存储
- 可插拔通讯适配器
- 轻量 Web 管理面板

DeepSeek Super-agent 主要提供事件驱动、任务协调和授权机制。

DSH 主要负责 Agent 会话、工具执行和自主扩展。

DSHA 作为设计参考，重点借鉴 Linux 工作环境、持久化和故障恢复经验。

不需要 Android 环境，不需要 PRoot。

**第一版不集成 Codex，不开发多执行引擎切换功能。**

DSH 使用的具体模型可以根据其支持情况配置，不要求必须使用某个固定模型。

## 十三、开发与部署要求

我们希望尽可能在一天内得到能够实际使用的 MVP。

不希望为了开发这个系统，需要人工持续监督几天、几周甚至一个月。

开发应优先由 AI 编程助手自主完成。

包括：

- 阅读开源项目。
- 研究源码。
- 搭建 Docker 环境。
- 修改代码。
- 安装依赖。
- 运行测试。
- 排查错误。
- 修复问题。
- 完成部署。
- 输出验收结果。

只有涉及必要凭据、账号授权、生产环境操作或重大技术阻塞时，才需要人工介入。

优先实现能够产生真实工作成果的功能。

不要把大量时间花在复杂 UI、非必要架构或重复开发上。

## 十四、第一版最低可用标准

第一版至少应该做到：

1. Agent 能在 Rocky Linux Docker 中正常运行。
2. 能通过一个实际通讯入口接收任务。
3. 能使用真实模型理解和执行任务。
4. 能在 Linux 环境中编写和运行脚本。
5. 能自主开发并复用至少一个工具。
6. 能记录任务并持续维护状态。
7. 能从后续消息中识别任务进展。
8. 能通过定时唤醒主动执行工作。
9. 能在容器重启后恢复数据和任务。
10. 能在必要时主动汇报成果。
11. 能阻止未经授权的敏感操作。
12. 能通过简单的 Web 页面查看运行情况。

### 第一版成功的实际表现

团队成员在群里正常讨论工作。

Agent 不需要被频繁 @。

它能够发现需要处理的事情，将其记录下来，并在权限允许时主动开始执行。

执行过程中，它可以使用 Linux 工具、编写脚本、分析数据和生成文件。

如果发现缺少工具，它可以自行开发。

完成工作后，它保存结果、更新任务状态，并在适当时机向团队反馈。

如果任务暂时无法完成，它会记录阻塞原因，在后续适当时间继续跟进。

**这就是我们希望第一版真正实现的工作方式。**

## 十五、明确不希望出现的设计

以下设计不符合本项目目标：

- 把 Agent 做成只能被 @才工作的普通聊天机器人。
- 把所有工作都变成必须人工明确下达的命令。
- Agent 没有自己的 Linux 执行环境。
- 每增加一种统计功能都必须人工开发插件。
- 把任务状态只保存在模型上下文里。
- 让 Docker 外部管理面板成为任务管理核心。
- Agent 每次启动都丢失此前的工作。
- 让 Agent 对群聊中的每条消息都回复。
- 为了实现简单功能引入大量不必要的服务。
- 为了兼容 Android 而保留 PRoot 等无关组件。
- 第一版引入多个执行框架，增加维护复杂度。
- 为了追求自我更新而允许 Agent 任意修改生产系统。
- 只交付设计文档，没有真正运行的系统。
- 使用模拟测试结果冒充真实功能验收。
- 需要用户长期盯着 AI 才能完成开发和部署。

## 十六、最终愿景

我们希望这个 Agent 最终成为公司的长期数字工作成员。

它能够理解公司正在推进的项目，知道哪些事情已经完成、哪些事情还没有完成、哪些工作存在阻塞。

它能够主动使用自己的 Linux 环境处理问题。

它能够不断积累工具、脚本、知识和工作经验。

它能够根据团队的反馈调整工作方式。

它能够在合理权限范围内自主完成越来越多的工作。

但它不应失去可控性。敏感数据、生产系统和高风险操作仍然必须遵循授权机制。

**最终目标不是让 AI 拥有无限权限，而是让 AI 在明确的权限边界内，尽可能独立、持续、有效地完成工作。**
